Fix the startup recovery configuration before shipping; the remaining findings concern audio contention, media preparation, LED behavior, and specific UI/upgrade defects. This is a review, not a patch: application source, deployment configuration, settings, and media were not changed.

Severity means: **High / P1** = address before shipping because a failure can leave the device unusable; **Medium / P2** = a feature or preparation workflow fails under the stated conditions; **Low / P3** = limited display, diagnostic, or upgrade defect.

**Numbered findings, highest severity first**

1. **High / P1 — The configured X session bypasses crash recovery and bounded logging.** [`.xinitrc`](/home/pi/.xinitrc:13) directly executes `python3 /home/pi/app/main.py` and redirects output to `xsession.log`. It never calls the existing [launcher](/home/pi/app/run_app.sh:28), so an unexpected process exit ends the app/X client without the implemented retry loop, and the implemented log rotation is also bypassed. On a device operated only by three GPIO buttons, that can require power cycling or remote intervention. This is a confirmed deployment configuration issue; the review did not deliberately crash the live session. **Fix:** retain the display environment/xset setup and execute `run_app.sh`, then verify a controlled crash is recovered on the device.

2. **Medium / P2 — Video and notification/SFX audio contend for the same exclusive device.** [Player output](/home/pi/app/src/video_archive/player.py:69) selects `alsa/default`, and [SFX playback](/home/pi/app/src/video_archive/audio.py:127) invokes `aplay` on the default device. The installed [ALSA configuration](/home/pi/.asoundrc:1) routes through `plug` directly to `hw:MAX98357A,0`, with no mixer. A chime while mpv owns the device can therefore fail instead of sounding. The existing `xsession.log` already contains `audio failed for select: ... Device or resource busy`. Waiting for audio before initial playback does not prevent chimes scheduled during the video. **Fix:** use a verified shared mixer/output path, or explicitly defer and retry notifications until playback releases the device. Test a new memo arriving during a video with SFX both on and off.

3. **Medium / P2 — Failed normalization leaves incomplete Gallery files that later runs silently accept.** The encoder writes straight to the final `.mp4` path with `-y`; [failure handling](/home/pi/app/tools/normalize_videos.py:310) does not remove the incomplete output. The [existing-file check](/home/pi/app/tools/normalize_videos.py:262) then skips that file on the next normal run. Reproduced with a simulated encoder that writes partial bytes and returns failure: the first run returned 1, the retry returned 0, and the encoder was not invoked again. With `--force`, a failed encode can also replace a previously working normalized copy with an incomplete one. **Fix:** encode to a temporary file and replace the final file only after successful validation. The 15 currently shipped files decoded successfully; this finding concerns subsequent preparation/re-encoding.

4. **Medium / P2 — Installing the declared PWM dependency can disable the status LED on this Pi.** [`_HardwarePWMLED`](/home/pi/app/src/video_archive/display.py:34) hard-codes `pwmchip2`. This device exposes `pwmchip0` and `pwmchip1`, not `pwmchip2`. When `rpi-hardware-pwm` is installed, [_create_status_led](/home/pi/app/src/video_archive/display.py:118) tries that backend and returns `None` after failure; it does not fall back to `PWMLED`. The review's virtual environment reproduced the missing-overlay/backend error. The system Python inspected here does not have that package, so it takes the other branch today; following `requirements.txt` can change that behavior. **Fix:** discover/configure the correct PWM controller/channel for the installed overlay, and preserve a tested fallback when hardware PWM initialization fails.

5. **Medium / P2 — Sleep Indicator percentages do not control sleep LED brightness.** [`sleep()`](/home/pi/app/src/video_archive/display.py:185) reduces the requested sleep brightness to a boolean. [`_set_status_led()`](/home/pi/app/src/video_archive/display.py:126) always uses the awake `_led_brightness` for every nonzero request. Reproduction with awake=50% and sleep=5% produced 50%; changing sleep to 100% still produced 50%. Only 0% behaves differently. With the saved settings inspected here, the requested 5% sleep level instead uses the 10% awake level. **Fix:** select the actual awake/sleep duty cycle rather than passing only an enabled flag.

6. **Medium / P2 — The documented video-preparation command reads the wrong source folder.** The [README](/home/pi/app/README.md:547) and deployment instructions say to place source files in `videos_raw/`, but [the CLI default](/home/pi/app/tools/normalize_videos.py:340) reads `videos/`. Following the documented instructions can therefore produce no new Gallery entries while reporting `No videos found` with exit status 0. The existing directory-default regression test fails for this reason. **Fix:** make the default and instructions agree; until fixed, use an explicit `--input-dir` pointing to the intended source folder.

7. **Low / P3 — Playback failures are not explained anywhere in the UI.** [`_playback_failed()`](/home/pi/app/src/video_archive/app.py:2665) prints the reason to a log, queues an error sound, and enters the same return flow as a normal exit. A missing/unreadable file, failed player startup, or startup timeout returns the three-button user to Gallery without displaying why. The user cannot access the logged diagnosis through the device. **Fix:** retain a visible error tied to the selected item, with a simple retry/back action. Existing media passed decoding; this affects error recovery rather than ordinary playback.

8. **Low / P3 — Long Settings and Admin text is visibly cut off at the target resolution.** [Settings detail text](/home/pi/app/src/video_archive/ui.py:1379) and [Admin status text](/home/pi/app/src/video_archive/ui.py:2042) use fixed rectangles without wrapping, fitting, or scrolling. At 1024×600, a valid 32-character ASCII network name required 518 px in a 509 px pane; a representative admin error required 778 px. Both were confirmed in rendered screenshots. This can hide the end of a network name or an error explanation. **Fix:** wrap status/error text within the available height and fit/elide network labels deliberately; provide a way to read a complete error when needed.

9. **Low / P3 — Wi-Fi diagnostics display the connection profile name as the SSID.** [`_wifi_status_worker()`](/home/pi/app/src/video_archive/app.py:1977) copies the `CONNECTION` field from `nmcli device status` into `current['ssid']`. A renamed profile or NetworkManager-generated name can differ from the actual wireless network. A stubbed status response with `Saved home profile` was displayed as the network name without any SSID query. This affects Settings, About, and Admin diagnosis. **Fix:** resolve the active connection UUID and read its actual wireless SSID, preserving its spaces/escapes as the scan code does.

10. **Low / P3 — Legacy sleep-brightness migration always uses the new default.** In [settings loading](/home/pi/app/src/video_archive/app.py:288), the fallback to `sleep_brightness` cannot run because `settings` was already populated with `DEFAULT_SETTINGS`, which always contains `sleep_led_brightness`. Reproduced with a settings file containing only `{"sleep_brightness":20}`: the result was 5, not 20, and the old key was removed from the loaded settings. A subsequent save loses the original preference. **Fix:** decide whether the new key exists in the original loaded dictionary before merging defaults.
